# Telegram Voice → Apple-Native Transcription — Feasibility Assessment (2026-07-16)

**Question.** Can swift-claw transcribe Telegram voice messages on-device with Apple's native speech APIs — voice message arrives → daemon downloads it → transcribes locally → transcript enters the standard text pipeline?

> **Verification key.** Every material claim carries a status: **✅ STABLE** (Apple's public docs for the shipping macOS 26 SDK, or official Telegram Bot API docs) · **🟢 CORROBORATED** (working OSS, reputable secondary sources, or hands-on SDK experiments on this machine — macOS 26.5.2 / Xcode 26.6) · **🟠 BETA** (macOS 27 only — not shipping) · **🟣 SPIKE** (needs a hands-on experiment to settle) · **🔴 REFUTED** (contradicted by primary sources or direct testing). Temporal frame: **July 2026** — macOS 26 "Tahoe" is shipping; macOS 27 is beta. Companion doc: `docs/research/apple-native-ai-2026-07-05.md` (the `ClawAppleAI` module proposal and the LaunchDaemon-vs-LaunchAgent spike, both of which this feature inherits).

> **How this was produced.** Four orchestrated research lenses (Apple Speech APIs, Telegram/audio formats, codebase seams, prior art), each adversarially verified claim-by-claim, including hands-on SDK experiments on the shipping target OS. One first-pass load-bearing claim was **refuted by direct testing** and is corrected throughout (the supposed mandatory Ogg→CAF/PCM decode step).

---

## 1. Verdict

**Yes — the full pipeline works on shipping macOS 26, in pure Swift, with zero third-party audio dependencies, and it was proven end-to-end on the target machine.** A Telegram-shaped voice file (Opus in Ogg, 48 kHz mono, libopus-encoded) opens directly with `AVAudioFile(forReading:)` — macOS now sniffs and decodes the Ogg container natively — and `SpeechAnalyzer` + `SpeechTranscriber` (macOS 26.0+, non-beta) transcribed it verbatim in ~0.3 s from a plain unsigned CLI binary with **no app bundle, no entitlement, no TCC prompt, and no authorization call**: Apple's permission doc explicitly scopes the authorization flow to the legacy `SFSpeechRecognizer` only. 🟢 CORROBORATED (reproduced twice, independently, on macOS 26.5.2). The engineering work is therefore not speech or audio — it is Telegram plumbing (the wire model currently discards the voice `file_id`; there is no `getFile`/download path) plus routing and taint decisions inside swift-claw. The one load-bearing unknown is the same one FoundationModels has: whether the out-of-process speech service is reachable from a true no-login-session `LaunchDaemon` (🟣 SPIKE, folded into the already-planned Stage-0 experiment; the likely deployment answer — LaunchAgent under auto-login — satisfies both features at once).

## 3. Pipeline design

End-to-end, anchored to the actual seams (file:line verified against this checkout):

1. **Detect.** Voice already rides the `"message"` update type the poller requests (`TelegramPollerService.swift:21`) — no `allowed_updates` change. Today `voice` decodes into the empty marker `TPresence` (`Sources/ClawTelegram/Wire/WireModels.swift:28,37`), discarding `file_id` before the update leaves the adapter, and the message dead-ends in the `.unsupported` arm with the canned "I can't read voice messages yet." (`MessageRouter.swift:109-111,145-153`). **Change:** decode a real `TVoice{file_id, duration, mime_type?, file_size?}` and thread a `.voice` content case through `RawMessage` → `IncomingMessage` (`IncomingMessage.swift:46-76`). ✅ STABLE (code)
2. **Fetch.** Add `getFile` + a byte download to `TelegramClient` — none exists today (full endpoint surface: `TelegramClient.swift:29-154`; repo-wide grep confirms zero download code). The shared seam already has a bounded GET (`HTTPExecuting.get(url:headers:timeoutSeconds:maxBodyBytes:)`, `Sources/ClawCore/Transport/HTTPExecuting.swift:53-58`; AsyncHTTPClient impl `Sources/ClawTelegram/Wire/HTTPExecuting.swift:43-64`), and `TelegramClient` already injects `any HTTPExecuting`. The download URL embeds the bot token — the new method must live inside `TelegramClient` to inherit `sanitize()` redaction (`TelegramClient.swift:202-204`). Cap `maxBodyBytes` well under the 20 MB Bot API ceiling. ✅ STABLE
3. **Stage.** Write to a private, byte-capped scratch directory under the state root, mirroring `ScratchWorkspace.create`/`ensurePrivateDirectory` (`Sources/ClawExec/Workspace/ScratchWorkspace.swift:15-57,154`; limits pattern from `ExecutionContracts.swift:22-39`). Delete after transcription. ✅ STABLE (pattern)
4. **Decode: no decode step.** Hand the downloaded file directly to `AVAudioFile(forReading:)` — macOS 26 opens Telegram's Ogg/Opus natively (content-sniffed; extension irrelevant), and bot-sent MP3/M4A decode natively too, so there is **no mime-type branching and no transcoder**. 🟢 CORROBORATED. Because this rests on undocumented CoreAudio behavior (`'Oggf'` has no public constant), check in one real Telegram voice note as a fixture and add a macOS-only integration test that decodes it to PCM — the tripwire for OS regressions. If a real-world file ever fails to open, that is a typed error path (reply "couldn't decode"), **not** a pipeline stage.
5. **Transcribe.** `SpeechTranscriber(locale:)` + `SpeechAnalyzer.start(inputAudioFile:finishAfterFile:true)` → accumulate `transcriber.results`. Guard availability with `SpeechTranscriber.isAvailable` and locale via `supportedLocale(equivalentTo:)`; fall back to `DictationTranscriber`, then to today's canned reply. Asset provisioning per §5. All of it lives in the macOS-only module (see below). ✅ STABLE (API) / 🟢 (headless)
6. **Enter the text pipeline.** Route the transcript **directly to `routePlain`**, bypassing `Command.parse` (`MessageRouter.swift:155`) — spoken text must not be able to trigger `/stop`-class commands. Borrow OpenClaw's contract: the transcript becomes the message body (with the voice provenance recorded), entering the normal turn flow. ✅ STABLE (code) / 🟢 (prior-art pattern)

**Where the transform sits: a domain-level `.voice` arm in `MessageRouter.route`, not the adapter and not a Tool.** The Tool option is structurally wrong for auto-transcription — an `.unsupported`/voice message never dispatches a turn, so no LLM is in the loop to call anything (`MessageRouter.swift:145-153`). The adapter option is impossible without reshaping it — `TUpdate.toRawUpdate()` is a pure synchronous mapping (`WireModels.swift:116-131`). That leaves the router, after the `isAllowed` check (strangers' voice notes never reach transcription).

**Inline-bounded, not persist-first — decided.** The poller awaits `router.handle` per update before advancing the cursor (`TelegramPollerService.swift:59-79`), and §6.1 requires claim+persist before cursor advance, so transcription before persist stalls intake for its duration. We accept that: this is a single-owner daemon with trivial message rates, transcription of a voice-note-length clip is sub-second, and the download is a bounded GET with an explicit timeout — worst case a few seconds of intake delay, with crash-mid-transcription safely covered by at-least-once re-delivery. The alternative (persist first, transcribe in the session lane) requires relaxing `InboundMessage`'s final-text-at-persist-time shape (`TurnDispatch.swift:22-37`, `Persistence.swift:120` — verified: no user-message text-update API exists on the session seam) — real invariant surgery for no v1 benefit. Revisit only if long audio or multi-chat ever makes the stall bite. ✅ STABLE (both horns' predicates verified in code)

**Module & portability.** All `Speech`/`AVFAudio` code goes in the macOS-only module (`ClawAppleAI` per the prior research, or a sibling `ClawAppleSpeech`) behind `#if canImport(Speech)` **plus** `@available(macOS 26, *)`/`#available` guards — `canImport(Speech)` is true on macOS 15 too, so it only excludes Linux; the version gate is separate. Package floor stays macOS 15 (`Package.swift:6`); CI gates ubuntu-24.04-arm and macos-26 (`.github/workflows/ci.yml:17,41`); this mirrors the `execute_code` feature-floor pattern (ARCHITECTURE.md §13: absent unless macOS 26 arm64, fails closed). Config flag `CLAW_VOICE_TRANSCRIPTION` in the `Keys` enum (`AppConfig.swift:5-43`, pattern `CLAW_EXEC_ENABLED` line 37); wiring at the composition root, which has moved since the prior research doc — `DaemonBuilder+Intake.swift:57` (`makeToolDispatcher`) and `DaemonBuilder+Agent.swift:90` (`makeAgent`), not `RunCommand.swift`. ✅ STABLE

## 4. Security & taint treatment

- **Every transcript is fenced as untrusted-labeled data. No exceptions in v1.** The wire model captures no forward metadata (`TMessage` decodes only message_id/from/chat/text/caption + six presence markers — no `forward_origin`; `WireModels.swift:30-41`), so the daemon cannot distinguish the owner's own voice note from a forwarded third-party one. Even with forward fields added, `MessageOriginHiddenUser` and copy-without-forward make provenance an unreliable trust signal. Under §12 (inbound content is data, never instructions), the safe default is to fence every transcript in `LabeledContext` (`ContextContracts.swift:179-197`, nonce-delimited `<claw-untrusted>`), accepting that the owner's own voice taints the session too. ✅ STABLE
- **Taint plumbing nuance — one small new seam, no gate changes.** The existing chain (`ToolPayload.ingestedUntrusted` → `TurnRunner` `setTainted:` at `TurnRunner.swift:366,433,463,585,610` → `sessions.tainted = 1` at `RunStoreGRDB+Helpers.swift:238`) is **tool-observation-shaped**: it only flips from dispatched ToolPayloads. A transcript spliced into inbound message text bypasses it. The integration must either mark the session tainted at inbound-persist time for `.voice`-origin messages (reusing the same store write) or surface the transcript through a ToolPayload-shaped seam. Either way: **zero `ToolPolicyGate` changes** — transcription is not egress, and its taint flag arms the existing downstream `web_fetch` trifecta gate exactly like `file_read`/`web_fetch` already do. ✅ STABLE (verified end-to-end)
- **No command parsing on transcripts** (see §3 step 6) — deterministic mitigation, enforced in code per the project's secure-by-default rule.
- **Cost & redaction.** Local transcription reports `costFromProvider = 0` (else `CostResolver` floors it and debits breakers for a free call — prior research §4). Transcript text passes through `SecretRedactor` + `ToolOutputCap`-style capping before entering context; the token-bearing download URL is redacted via the `TelegramClient.sanitize` precedent. ✅ STABLE (patterns)
- **On-device ≠ safe.** A transcript is attacker-influenceable text (anyone can speak a prompt injection into a forwarded voice note); prompt injection applies identically to on-device processing. Fencing + the existing in-code gates are the mitigation; nothing is relaxed.

## 5. Open unknowns / spikes

1. **🟣 The LaunchDaemon question (shared with FoundationModels — the one load-bearing unknown).** Every verified headless run (yap, both local experiments) executed inside a logged-in user session. SpeechAnalyzer inference runs out-of-process ("outside of your application's memory space", WWDC25 §277) and `isAvailable` has undocumented hardware gating; reachability from a true no-console-user `LaunchDaemon` is unverified in any source. Priors are *better* than FoundationModels' (no per-user Apple-Intelligence toggle; assets are system-wide, not per-user; no TCC gate at all). **Experiment:** extend the already-planned Stage-0 3-condition spike (`docs/research/apple-native-ai-2026-07-05.md` §6 — LaunchDaemon with no console user / SSH session / LaunchAgent, no-console verified via `stat -f%Su /dev/console`) with three Speech probes: `SpeechTranscriber.isAvailable`, an `AssetInventory` download of a fresh locale (asset download under no-session is a distinct failure point), and one file transcription. Same ~1-hour experiment; one deployment answer covers both features.
2. **🟣 Real Telegram file, not a synthetic one.** Both decode experiments used ffmpeg/libopus files identical in shape to Telegram voice notes (same codec, container, channel layout, sample rate) — residual risk is negligible but nonzero. **Experiment:** download one real voice note via `getFile` during Stage 1, confirm `AVAudioFile` decode, and check it in as the regression fixture from §3 step 4.
3. **🟢→field-hardening, not a spike: AssetInventory failure modes.** Field reports: `downloadAndInstall` can throw "asset not found after attempted download" for locales listed as supported (e.g. Arabic); status can wedge in `.downloading`; "Cannot use modules with unallocated locales" if `reserve(locale:)` is skipped; reserved-locale slots are limited (yap defensively releases stale reservations first). Also verified: `assetInstallationRequest` can return non-nil even when the model is installed (per-app reservation bookkeeping) — so call it unconditionally and idempotently, and use `SpeechTranscriber.installedLocales` (not request nil-ness) as the on-disk truth. Treat install as fallible with a typed error and the canned-reply fallback.

*(The two spikes from the first research pass — "does AVAudioFile read Opus-in-CAF" and "is a decode step needed at all" — were both resolved hands-on during verification: CAF-Opus reads fine, and no decode step exists. 🔴 The original mandatory-decode claim is refuted.)*

## 6. Staged roadmap

Flag-gated (`CLAW_VOICE_TRANSCRIPTION`, default off), Linux-green at every stage, each slice independently revertible.

- **Stage 0 — the shared deployment spike (½ day, before any feature code).** Run the extended 3-condition experiment from §5.1. Output: go/no-go for LaunchDaemon + the deployment shape. If LaunchDaemon fails, the LaunchAgent-under-auto-login answer already planned for FoundationModels covers this feature identically.
- **Stage 1 — Telegram plumbing (Linux-portable, no Speech).** `TVoice` wire decode + `.voice` domain content case; `TelegramClient.getFile` + bounded download with token redaction; staging directory. Behavior change: none visible (voice still gets the canned reply). Tests: wire decode, download bounding, redaction — all run on Linux CI. Capture the real-file fixture (§5.2).
- **Stage 2 — transcription slice (macOS 26 only).** The Apple-only module: availability probe, idempotent asset provisioning, `AVAudioFile → SpeechAnalyzer → transcript`. Router `.voice` arm: allowed-sender check → download → transcribe inline-bounded → fence + taint → `routePlain`. Fallback chain: `DictationTranscriber` → canned reply. Tests: taint propagation, unavailable-path fallback, the Ogg-decode regression fixture (macOS job), Linux build stays green (the module simply isn't compiled).
- **Stage 3 — polish.** Locale configuration (owner's language via `supportedLocale(equivalentTo:)`), typed errors surfaced as friendly replies ("couldn't transcribe: model not installed / unsupported language / decode failure"), duration guard for absurdly long audio.
- **Rollback.** Flag off → router falls through to today's `.unsupported` arm; `#if canImport(Speech)` keeps Linux compiling; each stage is a clean revert.

## 7. What we're NOT doing

- **No Whisper / WhisperKit / whisper.cpp fallback.** WhisperKit ingests via `AVAudioFile` (identical decode constraints, no format advantage), whisper.cpp needs external 16 kHz-WAV conversion; both add multi-GB model lifecycle and are ~2× slower than SpeechAnalyzer at comparable quality. 🟢
- **No third-party audio code.** No ffmpeg shell-out, no vendored libopus/libogg, no `element-hq/swift-ogg`, no Ogg→CAF remuxing — all contingency-only now that native Ogg/Opus decode is proven (and ffmpeg can't mux Opus-in-CAF anyway). 🔴 (the need was refuted)
- **No legacy `SFSpeechRecognizer`.** High-friction (embedded Info.plist + interactive TCC grant), truncation limits, strictly dominated by the modern stack on our OS floor. ✅
- **No macOS 27 beta APIs.** `AnalyzerInputConverter` / `AssetInputSequenceProvider` / `CaptureInputSequenceProvider` are 27.0-beta; noted, not adopted. 🟠
- **No live-microphone capture, no streaming/volatile results** — batch file transcription only (final results, default reporting options).
- **No voice replies / TTS** — inbound transcription only.
- **No language auto-detection** — the framework has none; locale is configured, with graceful fallback.
- **No local Bot API server** — the 20 MB getFile cap is a non-issue at voice-note bitrates; the escape hatch exists if ever needed. ✅
- **No trust tiering by forward-origin in v1** — everything is fenced untrusted; forward-metadata capture is a possible later refinement, with the caveat that hidden-user origins make it an unreliable signal even then.
