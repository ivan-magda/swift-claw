# How OpenClaw and Hermes Integrate MCP — and What swift-claw Should Take From Them

*2026-08-02. swift-claw has no MCP support; this studies two systems that do, to inform whether and how it should.*

## 0. Provenance

Read from primary source, not documentation summaries: an OpenClaw checkout at commit `a530a7bd`
(~165 MCP-related files under `src/`), a subset of Hermes' Python MCP modules and docs, and the
official `modelcontextprotocol/swift-sdk` client sources.

Numeric constants, config keys, file paths, and the swift-claw seam names were spot-checked against
those files after drafting. Claims that survived that check are stated plainly; the ones that could
not be closed are confined to §8. Three inherited-note corrections are marked inline where they
change a conclusion. The Hermes capture is a file subset rather than a full tree, so absence of a
thing in Hermes is weaker evidence than absence in OpenClaw.

## 1. What "supporting MCP" actually decomposes into

"Add MCP support" is not one feature. It is nine independent decisions, and both systems studied here answer all nine, sometimes in opposite directions:

- **Role** — client (consume other servers' tools), server (expose your own), or both. They are separate codebases with separate threat models.
- **Transport** — stdio child processes, SSE, Streamable HTTP; which ones, and what the daemon must own to run them.
- **Discovery** — when the tool list is fetched, how it is bounded, and whether a server may change it at runtime.
- **Naming** — a remote party supplies identifiers that must become collision-free, provider-legal function names.
- **Schema translation** — MCP `inputSchema` is JSON Schema written by strangers; LLM function-calling APIs reject dialects that JSON Schema permits.
- **Policy** — how a remote tool earns an authorization tier in a system that has one.
- **Auth to the server** — static headers, mTLS, or OAuth 2.1 with DCR and PKCE, plus where the tokens live.
- **Context cost** — tool schemas are billed on every turn, before any of them is used.
- **Lifecycle and failure** — connect, reconnect, pause, recycle, reap; and what happens to the agent turn when a server is down.

The rest of this study is those nine axes, answered twice, then mapped onto swift-claw's actual seams.

## 2. OpenClaw's approach

OpenClaw is both client and server, and keeps the paths strictly apart: `openclaw mcp serve` exposes OpenClaw over MCP; the `mcp.servers` registry is the client side, and its CLI verbs (`list`, `show`, `status`, `doctor`, `probe`, `add`, `set`, `configure`, `tools`, `login`, `logout`, `reload`, `unset`) are documented as touching only config. Everything except `login`, `probe`, and `doctor --probe` refuses to open a connection. That separation of "static check" from "live proof" is the single most transferable operational idea in the codebase: `doctor` catches missing stdio commands, bad working directories, missing TLS files, and literal secrets committed into `headers`/`env`, all without a network.

The config surface is a typed record per server (`oc/src/config/types.mcp.ts`): `command`/`args`/`env`/`cwd` for stdio; `url`/`transport` (`"stdio" | "sse" | "streamable-http"`)/`headers` for HTTP; `connectionTimeoutMs`, `requestTimeoutMs`, `supportsParallelToolCalls`, `enabled`, `sslVerify`, `clientCert`/`clientKey`, `auth: "oauth"` with an `oauth` sub-block (`scope`, `redirectUrl`, `clientMetadataUrl`, `authProfileId`), and `toolFilter: { include?, exclude? }` taking exact names or simple `*` globs.

Discovery is bounded hard. Tool listing runs through a shared paginator with `maxPages: 128`, `maxItems: 16_384`, `maxBytes: 10 MiB`, a repeated-cursor guard, and a per-request timeout; catalog assembly uses a 1.5 s list timeout and connects at most six servers concurrently (`agent-bundle-mcp-runtime.ts:88-95`). Naming is solved before registration: server and tool fragments are sanitized to `[A-Za-z0-9_-]`, the server prefix is capped at 30 characters and the joined `<server>__<tool>` at 64, collisions get numeric suffixes, and safe server names are assigned across the *full declared set in declaration order* so that adding a server cannot silently swap two existing names.

Two smaller decisions carry disproportionate weight. Tool descriptions pass through `sanitizeMcpMetadataText`, which rewrites "ignore/disregard (all) previous instructions" to `[redacted MCP metadata instruction]` and truncates at 1,200 characters before the text ever reaches a model. And input schemas are validated through an AJV/TypeBox-backed validator with draft-2020-12 detection and format stripping rather than trusted as-is.

Policy is layered outside MCP: MCP tools ride a `bundle-mcp` identity that agent tool profiles can hide (`minimal` does) or deny outright (`tools.deny: ["bundle-mcp"]`), and `toolFilter` prunes per server. What OpenClaw notably does *not* do is read MCP tool annotations — a grep of the entire `oc/src` tree for `readOnlyHint`, `destructiveHint`, `openWorldHint`, and `idempotentHint` returns nothing. A server's self-classification never influences authorization.

Failure handling is a small state machine: three consecutive tool failures pause that server for 60 s with a message naming the retry time, session-scoped MCP runtimes are reaped after 10 minutes idle, and — importantly — when credentials are unavailable OpenClaw omits that server from the agent runtime instead of failing the turn.

Authentication is the part the dossier examined at source. The OAuth 2.1 state machine is delegated to `@modelcontextprotocol/sdk`'s `auth()`, with OpenClaw supplying an `OAuthClientProvider` backed by a `mcp_oauth_stores` row: authorization-code + PKCE, dynamic client registration as a public client (`token_endpoint_auth_method: "none"`), RFC 9728 protected-resource-metadata discovery driven off `WWW-Authenticate`. For a headless daemon the shape is unusual and worth understanding: **there is no loopback listener and no device-code flow**. `openclaw mcp login <name>` prints a URL and exits; the operator reruns with `--code <code>`. The declared redirect (`http://127.0.0.1:8989/oauth/callback`, retried once as `localhost` if registration rejects it) is a fiction nothing binds to. Because the flow spans two processes, the PKCE verifier, DCR client information, and discovery metadata are all persisted — and the CSRF `state` deliberately is not: `state()` returns a fresh UUID per call, so the paste-back leg verifies nothing. OpenClaw's own Chutes OAuth refuses a bare code paste for exactly that reason.

Serialization is a cross-process SQLite lease (`core:mcp-oauth`, 60 s TTL, 30 s admission wait, heartbeat at TTL/3) whose loss aborts the in-flight OAuth request through `AbortSignal.any`, with every persisted mutation re-verifying ownership *inside the same write transaction*. OpenClaw also hand-rolls the 401/403 retry ladder above the SDK transport with an explicit comment that the SDK would otherwise refresh outside that lease, latches `insufficient_scope` into a sticky "run login again" state rather than retrying a refresh that cannot grant scope, and uses a compare-and-set on the rejected access token so a concurrent refresh is never clobbered.

Two audit corrections belong inline. The store is plaintext JSON — tokens, DCR secret, PKCE verifier — with `chmod 0700`/`0600` as the only at-rest protection; but the dossier's phrase "degrades to a warning" was **narrowed by the audit**: the helper rethrows on genuine permission failures and swallows only a narrow errno set (ENOTSUP/EOPNOTSUPP/EINVAL, plus EROFS/EPERM on provably restrictive targets). The load-bearing claim survives: no encryption at rest. Second, the logout tombstone (`credentialState: "cleared"`, never a row delete) plus parser invariants were described as making tombstones "unforgeable"; the audit **corrected that to rhetoric** — the invariants stop the legacy importer from resurrecting revoked credentials, they do not stop anyone with write access to the database, which is denial of service rather than resurrection.

OpenClaw's answer to context cost is two-tiered. Tool Search exposes `tool_search`/`tool_describe`/`tool_call` bridges. Code Mode goes further: the model-visible tool list collapses to `exec` and `wait`, model-written JavaScript runs in a QuickJS-WASI worker, and MCP tools are reachable *only* through a generated `MCP.<server>.<tool>({...})` namespace — they are deliberately omitted from the guest's generic `ALL_TOOLS`/`tools.search`/`tools.call` views while staying in the run-scoped catalog so policy, approvals, hooks, and telemetry still see the real tool id.

One security finding deserves separate billing. `audit-mcporter-registry.ts` bounds-reads a *third-party* MCP registry that OpenClaw never configured, because the audit's own text says the quiet part: agent skill filters are "not a shell-time authorization boundary. A host exec process can run external MCP clients or read a global mcporter registry unless sandbox, filesystem, network, or MCP credential boundaries block it." When it cannot inspect that registry, it emits a warning rather than skipping silently.

## 3. Hermes' approach

Hermes is client-first with an optional `hermes mcp serve` server mode. Config is a YAML map at `~/.hermes/config.yaml` under `mcp_servers`, with `command`/`args`/`env` or `url`/`headers`, `client_cert`/`client_key` (accepting a combined PEM path, a `[cert, key]` pair, or `[cert, key, password]`), `timeout`, `connect_timeout`, `enabled`, `supports_parallel_tool_calls`, and a `tools` block holding `include`/`exclude` plus `resources: false` / `prompts: false`. `include` wins over `exclude`; entries without glob metacharacters match exactly.

Naming is `mcp__<server>__<tool>` with every character outside `[A-Za-z0-9_]` replaced by `_`, chosen explicitly to match Claude Code/Codex/OpenCode and "the naming models are trained on" — the delimiter disambiguates the server/tool boundary when either half contains underscores. (Note a doc drift: Hermes' feature page still shows single-underscore `mcp_<server>_<tool>`; the config reference and `mcp_prefixed_tool_name` agree on the double form, so the code is authoritative.)

Schema translation is where Hermes is strongest, and it is the part most directly reusable. `_normalize_mcp_input_schema` applies four provider-portability repairs in one pass, each with a named provider that forced it: legacy `definitions` promoted to `$defs` (Kimi/Moonshot) — but *only* when `definitions` appears as a meta-keyword, never when it is the name of a property, because rewriting a user-facing property to `$defs` makes Anthropic and OpenAI reject the entire tool array; nullable `anyOf: [{...}, {"type":"null"}]` unions collapsed to the non-null branch (Anthropic); missing/`null` `type` coerced to `"object"` on object-shaped nodes; and `required` pruned to names that actually exist in `properties` (Gemini 400s otherwise). One remote server's sloppy schema breaks *every* conversation, not just that tool — which is why this normalization is defensive rather than optional.

Hermes' security posture on stdio is two-sided. `_build_safe_env` refuses to hand the process environment to a child: only `PATH`, `HOME`, `USER`, `LANG`, `LC_ALL`, `TERM`, `SHELL`, `TMPDIR`, a Windows location set, `XDG_*`, variables the configured secret backend explicitly tagged, and the server's own `env` block. Separately, `hermes_cli_mcp_security.py` refuses whole *config shapes*: a shell interpreter (`bash`, `sh`, `pwsh`, …) whose inline script contains network egress (`curl|wget|nc|socat|/dev/tcp/|Invoke-WebRequest`) or writes to an OS persistence surface (`authorized_keys`, `/etc/ssh`, `/etc/pam.d`, sudoers, cron, shell rc files), plus a hardcoded IOC blocklist — an attacker SSH key and source IPs — from a real June 2026 campaign that planted `command: bash` MCP entries Hermes then re-executed on every cron tick. Both checks run at save time *and* at spawn time, because a hand-edited or pre-planted config never passes through the save path. Error text returned to the model runs through a credential regex (`ghp_`, `sk-`, `Bearer …`, `token=`, `password=`) first.

Lifecycle is the most daemon-aware work in either project. Stdio servers can be recycled by `idle_timeout_seconds` and `max_lifetime_seconds` — motivated by `@playwright/mcp` keeping hundreds of MB of Chromium resident — and restart transparently on the next call while their tools stay registered. Keepalive pings fall back to `list_tools` when a server answers `ping` with method-not-found (structurally by JSON-RPC `-32601`, then by substring, because some servers phrase it as "Unknown method"). And stdio servers are not spawned directly at all: Hermes spawns a parent-death watchdog supervisor that execs the real command in its own process group, relays stdio verbatim, polls `getppid()`, and kills the process group the instant the original parent disappears — written because macOS has no equivalent of Linux's `prctl(PR_SET_PDEATHSIG)`, so a `kill -9`'d agent leaves orphans that race the next session for the same upstream session id.

**OAuth/PKCE as a distinct design.** Where OpenClaw refuses to bind a port, Hermes binds one: a real loopback `HTTPServer` on a reserved port, a browser opened when possible, and the authorization URL always printed. It then layers escape hatches for every way that fails in practice — a paste-back prompt accepting a full redirect URL, the provider's own callback URL, or a bare `?code=…&state=…` query string; `oauth.redirect_uri` for a proxied public callback (Tailscale Funnel) so a remote host needs no tunnel; `oauth.redirect_host: localhost` because at least one provider's WAF 403s any authorize request whose query string contains a literal `127.0.0.1`; pre-registered `client_id`/`client_secret` for servers that reject RFC 7591 dynamic registration (Google Drive returns 400 — and because that server serves `tools/list` unauthenticated, login *looks* like it worked until every real call times out, so `hermes mcp login` now checks that a token actually landed on disk); and an auto-set `client_name` for Figma, whose DCR allowlists client names by exact string. Crucially, the callback handler captures both `code` and `state` and returns them to the SDK's callback contract — the state is at least carried, unlike OpenClaw's bare-code paste. Storage is three files per server under `~/.hermes/mcp-tokens/<server>/`, written atomically at `0o600` (a TOCTOU fix over write-then-chmod), with snapshot/restore rollback if re-auth fails and a `poison_client_registration` path for a stale DCR client. Concurrency control is in-process only: an `asyncio.Lock` per provider entry guarded by a `threading.Lock` — no cross-process lease.

**The curated catalog as a distinct design.** Hermes ships an approved MCP list under `optional-mcps/<name>/manifest.yaml`, disabled by default; presence in that directory *is* the approval, granted by merging a PR, with no community tier. `hermes mcp install <name>` reads the manifest's pinned `manifest_version` (a newer one surfaces a "requires a newer Hermes" warning rather than hiding the entry), optionally `git clone`s and runs `install.bootstrap` commands, prompts for declared credentials and writes them to `~/.hermes/.env`, then **probes the server, lists its real tools, and presents a checkbox picker** whose result is written as `tools.include`. Pre-checks come from the user's prior selection first, then the manifest's `tools.default_enabled`, then everything; if the probe fails the install still succeeds with the manifest defaults. The docs are unusually honest about what this costs: installing runs the entry's own code, "so you should still read the manifest before installing."

Hermes' context-cost answer is Tool Search alone, with tiered disclosure. Tier 0 (no MCP/plugin tools) is pass-through; tier 1 replaces deferred schemas with three bridge tools plus a skills-style manifest of every deferred tool's name and short description, degrading *per server* so one oversized server collapses while small ones keep per-tool listings; tier 2 (the doc's example: Cloudflare's ~3,300 tools, whose names alone are ~32K tokens) drops to one line per server. Retrieval is BM25 over name + description + parameter names with a substring fallback for zero-IDF cases. Three properties are worth stealing outright: `tool_call` unwraps the bridge so hooks, guardrails, and approval prompts run against the *real* tool name; the catalog is rebuilt from the live tool-defs on every assembly rather than cached per session; and the catalog is scoped to the session's granted toolsets, so a restricted subagent cannot use the bridge to reach a tool it was not granted. Hermes also states its non-choice explicitly: "No JS sandbox… The JS-sandbox 'code mode' some other implementations offer is a large surface area; we skip it."

Finally, Hermes enables two server-initiated capabilities by default: sampling (a server asking Hermes' LLM to generate, bounded by rate limit, token cap, timeout, tool-round depth, and an optional model allowlist) and form-mode elicitation, routed into Hermes' existing approval surface with a 5-minute default; URL-mode elicitation is declined.

## 4. Where they agree, and where they genuinely diverge

They agree on more than the surface suggests: prefix-and-sanitize before registration; per-server `include`/`exclude` as the primary operator control; a static config file as the source of truth with no server-driven registration; plaintext tokens on disk protected only by file mode; delegation of the OAuth state machine to the language's MCP SDK; bounded discovery with failure cooldowns; "omit the broken server, don't fail the turn"; and — most tellingly — **neither reads MCP tool annotations**. `readOnlyHint` and friends appear nowhere in OpenClaw's source tree, nor in Hermes' captured MCP modules. Two independent teams concluded that a remote server's self-classification is not an authorization input.

The divergences are where their deployment assumptions show:

**OAuth completion.** OpenClaw binds no port and takes a bare code in a second CLI invocation, accepting the loss of CSRF state validation; Hermes binds a loopback listener, opens a browser, and treats paste-back as a fallback that still carries `state`. OpenClaw optimized for a headless gateway where a CLI process and a daemon process both touch one store and no browser exists; Hermes optimized for an interactive install moment, then bolted on four escape hatches for the headless case.

**Concurrency.** OpenClaw's cross-process SQLite lease with in-transaction fencing exists because its CLI and its gateway are different processes racing on the same row — an actor or mutex would be structurally insufficient. Hermes' in-process locks are sufficient exactly to the degree that its long-lived process is the only writer, and its docs quietly admit the seam: editing config inside a running session triggers a 30 s auto-reload that is "not enough for an interactive OAuth flow," so you are told to run `hermes mcp login` from a fresh terminal.

**Trusting server text.** OpenClaw *mutates* — rewrite injection phrases, truncate to 1,200 characters. Hermes *observes* — a ten-pattern scan that logs a warning and blocks nothing, because "false positives would break legitimate MCP servers."

**Distribution.** Hermes curates (reviewed manifests, one-click install, install-time tool checklist); OpenClaw documents recipes and invests instead in `doctor`/`probe` verification plus an audit that warns when it cannot even see a third-party registry a shell-capable agent might reach.

**Context bloat.** Both built tool search; only OpenClaw built code mode, and Hermes named the reason it did not.

**stdio hardening.** OpenClaw blocks *environment keys* that hijack an interpreter (`NODE_OPTIONS`, `PYTHONSTARTUP`, `DYLD_*`, `LD_*`, `BASH_FUNC_*`) with an allowlist so ordinary credential vars still work; Hermes blocks *config shapes* that look like malware. Same fear, different layer, and each is a partial answer to the other's gap.

## 5. The two hard problems everyone hits

**(a) Tool-definition context bloat.** The arithmetic is brutal and non-negotiable: schemas are re-sent every turn, before any tool is chosen, and one flat-API server can exceed the entire budget — Hermes' doc cites Cloudflare at ~3,300 tools whose *names alone* run ~32K tokens. There are exactly two families of answer in the evidence here. **Projection into code** (OpenClaw's code mode) hides every tool behind `exec`, and the model writes a program against a generated API; it buys loops, joins, and parallel calls in one round trip, and it costs a QuickJS-WASI runtime, a snapshot/resume lifecycle, and a host bridge that must preserve policy, approvals, hooks, and abort signals across the boundary. **Progressive disclosure** (tool search, both projects) keeps a search/describe/call bridge and defers schemas; it costs at least one extra round trip on cold tools, forfeits the system-prompt cache prefix for anything loaded mid-conversation, and inherits retrieval failure — the Anthropic numbers Hermes cites (49% → 74% on Opus 4) are as much a statement about the 26 points still missing as about the gain.

Two lessons transfer regardless of which family you pick. First, deferral makes capabilities *invisible*, and invisible capabilities get worked around: Hermes' benchmarking found models running `gh` in the terminal rather than searching for the deferred GitHub tool, or declaring a capability nonexistent. The fix was a name-level listing that stays visible at all times while schemas defer — capability discovery and schema loading are separate problems. Second, the catalog must be scoped to what the session was actually granted, or the bridge becomes a privilege-escalation path around toolset restrictions.

**(b) Trusting a remote server's self-described tools.** Every field a server returns — name, description, schema, annotations — is attacker-controlled text that reaches the model *before* any call is made, in the highest-trust position in the prompt. The systems here converge on refusing the server's own risk claims and disagree only on how much to launder the prose. But the deeper problem is that a tool catalog is a *time-varying* assertion: `notifications/tools/list_changed` means the thing you approved is not necessarily the thing you call, and any human review of a catalog is a snapshot. Hermes' install-time checklist and OpenClaw's `toolFilter` both convert a dynamic list into a pinned allowlist for exactly this reason. Name collision is the other half: a server that names its tool `read_file` is attempting a namespace squat on your built-in, which is why both sanitize, prefix, and suffix collisions before registration rather than after. And OpenClaw's mcporter finding closes the loop on the ambient case — if the agent can run a shell, it can reach MCP servers you never configured, and no amount of catalog curation is a boundary; only sandbox, filesystem, network, or credential isolation is.

## 6. What this means for swift-claw

**Be a client, not a server.** swift-claw is single-owner and Telegram-fronted; exposing an MCP server means a second authenticated ingress with its own grant lifecycle. Nothing in the study argues for it.

**HTTP first; stdio deliberately deferred.** Streamable HTTP reuses `HTTPExecuting` and `DaemonBuilder.toolExecutor` (`DaemonBuilder.swift:23`) and inherits the SSRF discipline already in the codebase. stdio would require the daemon to own child-process supervision under launchd — and Hermes' watchdog supervisor exists precisely because macOS lacks `PR_SET_PDEATHSIG`, meaning the orphan problem is a *macOS daemon* problem, not a theoretical one. It would also require re-deriving OpenClaw's interpreter-hijack env blocklist and Hermes' config-shape refusals, and it would grant unsandboxed local code execution to whatever a config file names, which is incoherent next to an `ExecuteCodeTool` that runs inside a sandbox backend.

**Take the SDK's `Client`, write your own `Transport`.** `Transport` is declared `public protocol Transport: Actor` — 20 lines, a `logger` and four members (`connect`, `disconnect`, `send(Data)`, `receive() -> AsyncThrowingStream<Data, Swift.Error>`). That it is an actor-constrained protocol is a gift under strict concurrency: a custom AsyncHTTPClient transport inherits its own isolation domain without further ceremony. `Client` imports nothing but Logging and Foundation's JSON coders — it is transport-agnostic. That is the seam to use. Re-deriving what `Client.swift` (1,145 lines) and `Messages.swift` (427 lines) already do — framing, id correlation, cancellation, batching, pagination cursors, protocol types — is the work you skip. What you must *not* take is `HTTPClientTransport` (686 lines): it is `URLSession`-based, which on Linux means FoundationNetworking as a second HTTP stack beside AsyncHTTPClient, bypassing the existing executor seam; and its Linux branch, on receiving a spec-legal `text/event-stream` response to a POST, logs "SSE responses aren't fully supported on Linux" and yields the raw SSE bytes into the message stream as if they were JSON. For a package that ships macOS *and* Linux, that is disqualifying. Two adoption caveats: the SDK's `Package.swift` is `swift-tools-version:6.1` (swift-claw is 6.0) and gates its EventSource dependency to Apple platforms, and it depends on swift-docc-plugin at `branch: "main"` — a moving reference in a release build. On the plus side, `Client.Capabilities()` defaults sampling, elicitation, and roots to `nil`, so those stay off unless you register handlers. Keep them off.

**One `Tool` conformance per remote tool, built at boot.** The protocol at `ToolContracts.swift:256` is the checklist and it is well-suited: `definition`, `timeout` (use the per-server request timeout), `canonicalTarget`, `prepareAction`, and a non-throwing `execute` that turns transport failures into `ToolPayload` with `.error`. `prepareAction` is not optional in practice — its doc states the gate fails closed when a dangerous tool returns `nil`, so the tier an MCP tool is given and what it returns here have to be decided together. The single most important line in the whole integration is `ingestedUntrusted: true` on every MCP result, because that is what feeds `runIngestedUntrusted` into the trifecta condition at `ToolPolicyGate.swift:66-68`. An MCP result is by definition untrusted inbound.

**Naming must be total before `ToolRegistry`.** `ToolRegistry.init(tools:)` builds `Dictionary(uniqueKeysWithValues:)` and *traps* on duplicates — with remote-supplied names, that is a remote-triggered daemon crash. Do what both projects do: sanitize to a provider-legal charset, prefix with the server name, and apply a deterministic collision suffix, all before construction — plus one swift-claw-specific rule neither needed: if a sanitized MCP name collides with a built-in tool name, the built-in wins and the MCP tool is renamed, never the reverse.

**Normalize schemas at ingestion, not in the encoders.** `ToolDefinition.parameters` is a `JSONValue` that `OpenAICompatibleProvider.swift:192` and `ChatGPTResponsesRequestEncoder.wireTool` (:217) pass through verbatim, so a malformed remote schema reaches the provider unmodified and 400s the whole request — including the built-in tools in the same array. Re-derive Hermes' four repairs (`definitions`→`$defs` with the property-name gate, nullable-union collapse, missing-`type` coercion, `required` pruning) at the MCP boundary, where they cannot affect built-in definitions. Cap remote descriptions the way OpenClaw does; skip the phrase-rewriting, which is a filter that fails open and buys a false sense of safety — the durable control is the tier, not the regex.

**Tier comes from the owner, never the server.** Default every MCP tool to `riskLevel = .ask` and `egressClass = .arbitraryDestination`, downgradable only by an explicit owner config entry naming the server and tool. Return `.resolved` of the *server identity* from `canonicalTarget` (ask-tier fails closed on `nil`), so the Telegram approval prompt names the server rather than a destination the server chose. `ApprovalReason.askTier` already covers this without new owner-facing copy.

**Pin the catalog; do not implement live `list_changed`.** `PolicyFingerprint.StaticInputs.tools` folds tool names, canonical parameter JSON, `riskLevel`, and egress into `policy_version`, and a change voids parked approvals as `stale_policy`. That is correct, and it means a server that reshuffles its tools mid-session silently invalidates the owner's pending approvals — and churns `ChatGPTPromptCacheKey.make(instructions:tools:)` at the same time. Snapshot the catalog at boot; refresh only on an explicit owner-initiated restart. Include MCP definitions in `staticSubhash` exactly like built-ins.

**swift-claw has OpenClaw's two-process problem, not Hermes' one-process one.** This decides the store's shape before anything else. A `clawd` CLI invocation and the launchd daemon are separate processes that would both write a token row, which is exactly the situation OpenClaw's SQLite lease exists to serialize and exactly the situation Hermes' `asyncio.Lock` would not survive. A Swift actor is equally insufficient for the same reason — it serializes within a process. Either take a lease/CAS discipline in the database, or make it structurally impossible by declaring the daemon the sole writer and having the CLI hand tokens over through it. Key rows the way OpenClaw does, on server name *and* a hash of its URL, so a re-pointed server does not silently inherit credentials for a different host.

**Credentials: a new store, not a fourth `Secrets` field.** `Secrets` is a closed three-field struct whose `redactionValues` is derived from those fields; per-server tokens need a map, which changes both. Put them in the existing GRDB database behind the store discipline the project already mandates (`writeMapping`/`readMapping` → `ClawDatabase.classifyError` → `StoreError`), and encrypt the token column with the same swift-crypto AES-GCM envelope `EncryptedFileSecretStore` already uses — both studied systems store tokens in plaintext behind file mode alone, and swift-claw already owns the primitive that does better for near-zero cost. Feed resolved token values into the redaction set so a token can never reach a Telegram message.

**One design tension on the execution paths — not two bugs.** `ToolPolicyGate.executeWithTimeout` (private, `ToolPolicyGate.swift:443`, reached from `:424`) abandons the losing task on timeout. `ApprovedActionExecutor.swift:161` deliberately does *not* use it, and says so in place: "Run to completion on the waiter task — direct await, NEVER `executeWithTimeout`'s abandon-on-timeout race, so the observation is always truthful (file_write is atomic)."

Both sides of that are correct today and both are correct *because tool calls are local*. MCP breaks the shared premise. On the gate path, an abandoned `tools/call` may still land server-side, so the timeout stops being an abort and becomes at-most-once-unknown. On the approval path, "run to completion" means a remote server can wedge an approved action indefinitely. The resolution is a single decision about what a remote call's timeout *means* — not a patch to each site, and specifically not "add a timeout to `ApprovedActionExecutor`," which would revert a stated invariant. The honest options are to make MCP calls cancellable end-to-end (send `notifications/cancelled` and await acknowledgement before abandoning) or to document remote execution as at-most-once-unknown and keep approvals bounded by a deadline the owner sees.

**Config needs a real file, and `makeToolDispatcher` needs a signature change.** `AppConfig.load` reads only the environment, and the flat `KEY=value` env file cannot express a server list without inventing an encoding. Add a small YAML file parsed with Yams, read once at boot. Note the cost honestly: Yams is declared on the `ClawWorkspace` target only (`Package.swift:48`), while `AppConfig` lives in `ClawCore` — so this is a new dependency edge on a low-level module, not a free reuse. Parsing the file in `ClawWorkspace` and handing the result down avoids that. `DaemonBuilder.makeToolDispatcher` (`DaemonBuilder+Intake.swift:117`) is synchronous and non-throwing, so resolve the MCP catalog in an async step inside `makeAgentStack` and pass a resolved tool list *into* `makeToolDispatcher`, leaving the gate wiring untouched. Bound that resolution the way OpenClaw does — short list timeout, small connect concurrency, page/item/byte caps — and skip a failing server rather than failing the daemon.

**Defer the disclosure machinery.** With six built-in tools and one or two personal servers, eager definitions are correct. The trigger to revisit is not token count but prompt-cache stability.

## 7. What not to copy

- **OpenClaw's stateless `state()` plus bare `--code` paste.** No CSRF validation whatsoever, on a flow that mints credentials. If swift-claw ever does OAuth rather than a static token, persist `state` alongside the verifier and verify on return — Hermes carries it back, and OpenClaw's own Chutes flow refuses a bare code for this reason.
- **Plaintext token storage protected only by file mode.** Both do it; swift-claw already has the envelope to avoid it. (The audit's narrowing of "best-effort chmod" changes the severity, not the conclusion.)
- **The tombstone scheme and the `-lock`/`-lock-stale` legacy-migration protocol.** These exist to protect a *retired file-based store* from a still-running old binary during import. swift-claw has no legacy store; deleting a row on logout is fine. And the audit was explicit that the tombstone invariants are not tamper-proof.
- **Sampling and elicitation enabled by default.** A remote server spending the owner's tokens and steering the model, or opening an unbounded interactive prompt mid-call, are both indefensible under default-deny. The SDK's defaults are already `nil`; leave them.
- **MCP annotations as a policy input.** Neither project trusts them; neither should this one.
- **Token projection into child-process environment variables** (`OPENCLAW_MCP_AUTH_*`). It exists to feed external CLI runtimes swift-claw does not have.
- **Code mode's QuickJS-WASI guest.** Hermes' own judgement — "a large surface area; we skip it" — applies with more force to a single-owner Swift daemon.
- **`sslVerify: false` as a config knob**, and any auto-installer that clones a repo and runs `install.bootstrap` commands. The *manifest idea* (declared transport, auth, and default tool selection, reviewed before use) is worth copying; the installer is a supply-chain hole with a review label on it.
- **Runtime server management verbs *reachable by the agent*.** Even OpenClaw's CLI is documented as "these commands only read or write config." The line to hold is that no tool the model can call may add a server or mint a credential — not that `clawd` grows no subcommands. An owner-run `clawd mcp login` on the operator's terminal is the opposite of a risk; it is the only way a token ever legitimately reaches the store proposed above, and §6's encrypted per-server store presupposes one. Keep the verbs, keep them out of `ToolRegistry`.

## 8. Open questions the research could not close

Whether either implementation sends RFC 8707 `resource` indicators on authorization and token requests is **undetermined** — both delegate request construction to an SDK that was not in the capture (only RFC 9728 protected-resource-metadata plumbing is verified for OpenClaw). Whether a *used* PKCE verifier is ever deleted from OpenClaw's plaintext row is also undetermined: `saveTokens` clears provenance fields but not `codeVerifier`, and the only removal path runs through SDK-internal `invalidateCredentials` call sites. Whether the Python MCP SDK actually validates the `state` Hermes hands back is unverified for the same reason.

The single most decision-driving unknown for a Swift build: the `HTTPClientAuthorizer` protocol declaration is not in the capture. The transport's *use* of it is verified in detail (`validateEndpointSecurity` → `prepareAuthorization` → `authorizationHeader` → `handleChallenge` with a bounded retry) — which **corrects** this project's earlier notes treating the Swift SDK's transport as bearer-header-only — but whether the SDK ships a concrete OAuth 2.1 implementation with token storage, PKCE, and DCR, or only the seam, is unresolved.

Smaller unresolved items: which MCP spec revision OpenClaw's authorization behavior targets (no revision string appears in its five OAuth files; the Swift SDK, separately, does send an `MCP-Protocol-Version` header, defaulting to `Version.latest` = `"2025-11-25"` — `HTTPClientTransport.swift:64-65,106,115`); whether column-level encryption is applied anywhere else in OpenClaw's state-db subsystem, which was not audited beyond the store read/write path; whether Hermes reads annotations outside its captured MCP modules, since that capture is a file subset rather than a full tree; Hermes' own doc drift on single- versus double-underscore tool naming; the mcporter registry schema beyond `{mcpServers: {<name>: {enabled?}}}`; and whether the gateway-side MCP grants in `gw/mcp-grant-store.ts` (in-memory, 1 h default TTL) are ever persisted or logged — that file turned out to be server-side and outside the client credential story entirely.
