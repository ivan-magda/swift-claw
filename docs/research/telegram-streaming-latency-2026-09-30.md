# Задержка потокового ответа в Telegram: диагностика

Дата: 2026-09-30.
Статус: диагностика завершена. Исправление не определено.
Файл не добавлен в git.

## Термины

- **Провайдер** — сервис модели: OpenRouter или ChatGPT-подписка.
- **SSE** — формат потоковой передачи по HTTP. Провайдер отправляет ответ частями.
- **Дельта** — одна часть текста ответа из SSE-потока.
- **Адаптер** — код swift-claw, который читает SSE-поток (`OpenAICompatibleProvider`, `ChatGPTResponsesProvider`).
- **Runtime** — код агента, который собирает дельты и отправляет черновики (`StreamingTurnRuntime`).
- **Черновик** — временное сообщение Telegram (`sendRichMessageDraft`). Клиент показывает его во время генерации. Изменения черновика клиент анимирует.
- **Итоговое сообщение** — постоянное сообщение (`sendRichMessage`). Его отправляет outbox после конца хода.
- **Ход (run)** — обработка одного сообщения пользователя. Ход с инструментами состоит из нескольких запросов к модели (раундов).
- **Раскрытие** — анимация клиента Telegram: текст черновика появляется на экране постепенно.

## Вывод

Задержка воспроизводится. Её создают не провайдер и не swift-claw.

- Провайдер отдаёт текст постепенно.
- swift-claw отправляет каждый черновик через 0,1–0,3 с после появления текста.
- Отставание создаёт анимация клиента Telegram for macOS 12.10.
- Первый текст виден на экране примерно через 2 с после прихода от провайдера.
- Раскрытие заканчивается примерно через 3,7 с после конца генерации.
- Около 70 % анимации идёт после того, как модель закончила.

Регрессию в коде swift-claw подтвердить не удалось.

## Как измерено

1. **Контроль провайдера.** Запрос через `curl` с `Accept-Encoding: identity` и с `gzip`. Скрипт на Python ставит время на каждое чтение из сокета и на каждое SSE-событие.
2. **Стенд.** Временный тест в отдельном worktree. Используются реальный адаптер OpenRouter, реальный `StreamingTurnRuntime` и записывающий приёмник черновиков. В Telegram стенд ничего не отправлял.
3. **Сквозной прогон.** Временная сборка `clawd` с метками времени (мс) и с конфигурацией владельца. Метки стоят на границах участков:
   - приём сообщения (`TurnDispatch`);
   - HTTP-чанк (`AsyncHTTPExecutor.forward`);
   - дельта адаптера (`OpenAICompatibleProvider.consume`);
   - дельта в runtime и конец потока (`StreamingTurnRuntime.consumeStream`);
   - отправка черновика и её HTTP-вызов (`runDraftAndTypingLoop`, `TelegramRichDraftStreamer`);
   - `typing` (`TelegramTypingIndicator`);
   - финальный черновик и `sendRichMessage` (`OutboxDispatcher.send`).
4. **Видео.** Запись экрана Telegram for macOS 12.10 во время сквозного прогона.
   - Лог и видео сопоставлены по двум отправкам сообщений. Интервал между ними 25,37 с и в логе, и на видео.
   - Проверка: превью в списке чатов меняется через 0,11 с после ответа `sendRichMessage`.
   - Точность сопоставления около 0,1 с.
5. **Маршрут ChatGPT.** Та же сборка с `CLAW_LLM_MODEL=openai-chatgpt/gpt-6-sol`. Есть только лог, видео нет.

## Записи пользователя до диагностики

В логах нет миллисекунд, поэтому точность здесь около ±1 с.

| Запись | Ход | Текст на экране | Ход закончен | Раскрытие закончено |
|---|---|---|---|---|
| `screen-recording-chatgpt-subscription.mov` | run 281 | t≈15,8 | t≈17,7 | t≈21,0 |
| `screen-recording-openrouter.mov` | run 282 | t≈23,9 | t≈26 | t≈29,5 |

В обеих записях раскрытие заканчивается примерно через 3 с после конца хода.

Запись «ChatGPT-подписка» на самом деле шла через OpenRouter. Доказательства:

- в логе run 281 стоят `model=openai/gpt-6-luna` и `chat stream request`; эту строку пишет только OpenAI-совместимый адаптер;
- в OpenRouter есть две генерации в 15:53, по одной на каждый раунд run 281.

## Чем объясняется поведение

1. При запросе с инструментами первого текста нет 14,4 с. Всё это время виден только «typing». Это ожидаемо.
2. gpt-6-luna выдаёт весь ответ примерно за 3,5 с.
3. Клиент не показывает текст первого черновика. Текст появляется только после второго, примерно через 1,5 с.
4. Клиент раскрывает текст медленнее, чем пишет модель. Итоговое сообщение приходит через 0,1 с, но анимация идёт ещё около 3,4 с.

Пользователь видит долгое «typing», потом около 5 с анимации. Примерно 3,7 с из них идут после конца генерации.

## Регрессия и история изменений

- Интервал между черновиками был около 1,2 с до `c0425cd8` (2026-07-02): 120 проверок по 10 мс. После него интервал 5 тиков по 250 мс плюс HTTP-вызов, то есть 1,3–1,5 с.
- `sendRichMessageDraft` используется с первого дня.
- Переделка потоков в июле (`0cc534f1`, `b97ffedc`, `81ab143a`) задержки не добавляет. В текущем коде переходы занимают меньше 1 мс.
- Поддержка ChatGPT (с 2026-07-16) не затрагивает путь OpenRouter.
- Гипотеза про `gzip` не подтвердилась: OpenRouter не сжимает SSE.

## Маршрут ChatGPT (run 286)

- Поток идёт постепенно.
- Первый текст пришёл через 4,46 с после приёма сообщения.
- gpt-6-sol выдал 2010 символов за 22,6 с, около 89 символов/с.
- swift-claw отправил 16 черновиков примерно каждые 1,4 с.
- Итоговое сообщение ушло через 0,21 с после конца потока.

## Чего не хватает

- Какая модель и какая версия клиента Telegram были «несколько месяцев назад». Модель можно найти в OpenRouter Activity по датам.
- Правдоподобная, но не проверенная причина «раньше было лучше»: прежняя модель писала не быстрее анимации клиента.
- Видео маршрута ChatGPT. По расчёту, при 89 символах/с клиент успевает за моделью. На экране это не проверено.
- Как устроена анимация клиента. Непонятно, ждёт ли клиент второй черновик или держит фиксированную паузу около 1,5 с. Это проверяется опытом с другим интервалом черновиков. Проверено позже: клиент ждёт второй черновик (раздел «Проверка гипотез»).

## Гипотезы для этапа исправления

- Более ранний второй черновик раньше запускает раскрытие текста. **Подтверждена**, см. «Проверка гипотез», A.
- Без финального черновика перед `sendRichMessage` хвост анимации короче. **Не подтверждена**: выигрыш около 0,1 с, см. B.
- Показывать ход работы во время инструментов, например блоком `<tg-thinking>` в черновике. Отдельная задача, issue #239.

## Проверка гипотез

Дата: вечер 2026-09-30. Клиент тот же: Telegram for macOS 12.10 (сборка 282985). Тёмная тема, окно на правой половине экрана.

Итог:
- **A подтверждена.** Текст появляется примерно на 1 с раньше.
- **B не подтверждена.** Хвост короче примерно на 0,1 с.
- **C не подтверждена.** Код concurrency на пути стриминга не даёт заметной задержки. Гонок данных не найдено.

### Как проверено

- **Стенд воспроизведения.** Фиксированный текст (2103 символа, 6 абзацев) и график дельт из run 284 (508 непустых дельт за 3,45 с). Дельты идут через настоящий `StreamingTurnRuntime`. Typing, черновики и `sendRichMessage` уходят в Bot API, в чат владельца. Демон владельца работал. Стенд обновления не опрашивает.
- **Реальный путь.** Тот же стенд с настоящим OpenRouter `openai/gpt-6-luna` и промптом из исходного протокола. Gateway и outbox не участвуют: итоговое сообщение стенд отправляет тем же вызовом `sendRichMessage`.
- **Варианты.** В каждом меняется один параметр:
  - `a-early` — второй черновик через 1 тик, ≈0,34 с после первого.
  - `a-late` — второй черновик через 10 тиков, ≈2,68 с. Это контроль механизма, не кандидат на правку.
  - `b-nofinal` — без финального черновика.
- **Видео.** Запись экрана 60 кадров/с без потерь. Поверх окон висят часы с двоичным таймкодом (epoch ms). Время каждого кадра читается из самого кадра. Точность около одного кадра (17 мс). Отклонение от линейной подгонки −48…+14 мс.
- **События в кадре.** Каждое правило проверено на кадрах.
  - «Текст виден»: яркие пиксели в нижней полосе чата.
  - «Final получен»: строка чата в списке перестаёт показывать «typing» и показывает превью.
  - «Раскрытие закончено»: последнее изменение в области чата.
- **Объём.**
  - Этап 1: 16 прогонов воспроизведения, по 4 на вариант. Порядок сдвигается по блокам.
  - Этап 2: 8 прогонов с OpenRouter: 3 baseline, 3 a-early, 2 b-nofinal.
- **Ответы API.** 90 вызовов `sendRichMessageDraft`, 24 `sendRichMessage`, 24 `sendChatAction`. Ошибок и flood control нет.

- Во всех 20 прогонах, где второй черновик пришёл раньше 1,9 с, текст появился через 0,06–0,13 с после него.

- Механизм (контроль a-late): клиент не раскрывает текст первого черновика, пока не придёт второе обновление. Примерно через 1,95 с без обновлений он показывает одну букву и ждёт. Это видно в прогонах 3 и 9.
- Предел эффекта: конец раскрытия не сдвигается. На воспроизведении время от первого токена до полного текста равно 7,12 с в baseline и 7,09 с в a-early. Раскрытие начинается раньше и идёт медленнее.
- Цена: обычно на один черновик больше за раунд. Ошибок API в a-early нет.

### C: сложность или ошибки concurrency на пути стриминга — не подтверждена

| Участок | Результат |
|---|---|
| HTTP-чанк → `rt.delta` (OpenRouter, 2918 чанков) | медиана 0,20 мс, максимум 2,0 мс |
| Дельта провайдера → `rt.delta` (воспроизведение, 8128 дельт) | медиана 0,10 мс, p99 0,20 мс, максимум 0,40 мс |
| Конец тела HTTP → конец потока в runtime → решение гонки → финальный черновик | не больше 0,2 мс на переход |
| Первая дельта с текстом → первый черновик | 12–266 мс: ожидание тика 250 мс |
| Интервал черновиков | медиана 1,39 с: 5 тиков по 250 мс плюс HTTP |
| Последняя текстовая дельта → конец тела HTTP (OpenRouter) | 70–206 мс: usage и `[DONE]` от провайдера |
| Финальный черновик перед `sendRichMessage` | 80–100 мс HTTP |

- Код concurrency добавляет доли миллисекунды. Пользователь видит две задержки клиента: ожидание второго черновика (около 1,4 с) и раскрытие после final (около 3,4 с).
- Thread Sanitizer: 143 теста в 9 наборах прошли без предупреждений. Наборы: `BoundedAsyncChannelTests`, `LLMEventStreamTests`, `ProviderDeadlineCoordinatorTests`, `AgentRuntimeStreamingTests`, `AsyncHTTPExecutorStreamingTests`, `HTTPStreamExchangeOwnershipTests`, `OpenAICompatibleProviderTests`, `ChatGPTResponsesProviderCancellationTests`, `TelegramRichDraftStreamerTests`.
- Сложность кода:
  - На этом пути работают два ограниченных канала, владелец завершения потока, гонка трёх задач с lock-победителем и актор снимка.
  - Этого требует архитектура §8.4: владеющий поток, синхронная отмена, join на каждом выходе, кэш терминального ответа до закрытия канала, обратное давление транспорта.
  - Упрощение — это архитектурное решение. Замеры задержки его не оправдывают.
- Найдено одно поведение, не связанное с задержкой:
  - `TelegramRichDraftStreamer.sendDraft` глотает все ошибки, включая `TelegramError.floodControl(retryAfter:)`.
  - После неудачной отправки цикл повторяет черновик на следующем тике с новым текстом, то есть примерно каждые 0,25 с. `retry_after` он не ждёт.
  - Outbox для итоговых сообщений `retry_after` соблюдает.
  - В прогонах ответов 429 не было.

### Проверка правки на демоне

Ветка `feature/early-second-draft`, коммит `a98d3ef4`: второй черновик через один тик (250 мс) и пауза черновиков по `retry_after`.
Демон из ветки с временными метками запускался с конфигурацией владельца. Путь полный: сообщение владельца → gateway → OpenRouter → черновики → outbox.

| Прогон | Второй черновик | Первые буквы на экране | Конец раскрытия после конца потока |
|---|---:|---:|---:|
| run 288 | 0,32 с | ≈0,45 с | 3,68 с |
| run 289 | 0,36 с | ≈0,50 с | 3,60 с |
| run 290 | 0,34 с | ≈0,45 с | 3,75 с |

- Время отсчитано от доставки первого черновика.
- Первые буквы определены по кадрам с шагом 50 мс. Автоматический детектор здесь не подходит: в нижней полосе стоит сообщение владельца.
- До правки текст появлялся примерно через 1,5 с после первого черновика. Теперь около 0,5 с.
- Конец раскрытия не изменился, как и ожидалось.
- Ошибок API нет. Итоговые сообщения полные.

  - Раскрытие продолжается с той же позиции.
  - Это видно во всех вариантах, включая b-nofinal.
- **Новая группа.** Первое сообщение после паузы открывает новую группу: аватар и имя бота появляются вместе с пустым пузырём.
- **Раскрытие после final.** На реальных ответах оно длится от 1,7 до 3,5 с, на воспроизведении — постоянно 3,37–3,52 с. От чего зависит длительность, не установлено.

### Чего не хватает

- Прогона на полном пути демона, с gateway и outbox. Для вывода по A он не нужен: эффект возникает до конца потока. Для постоянной правки нужен обычный прогон демона.
- Других клиентов и тем: iOS, Telegram Desktop, светлая тема. Маршрута ChatGPT.
- Модели анимации клиента: от чего зависит скорость раскрытия после final.
